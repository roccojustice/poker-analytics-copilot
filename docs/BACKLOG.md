## Next up (active)
- [ ] **`json.JSONDecodeError` safety net lost in the tool-calling migration (found Session 36, 2026-08-21):** the old `parse_user_query()` wrapped `json.loads(content)` in a `try/except json.JSONDecodeError: return {"query_name": "unknown"}`. The rewritten version (`llm_parser.py:86`, `args = json.loads(tool_call.function.arguments)`) has no `try/except` around it — if the model ever returns a malformed `arguments` string, this now raises an uncaught `JSONDecodeError` instead of falling back to `"unknown"`. Found while redesigning `tests/test_llm_parser.py`'s `test_parse_user_query_unknown` for the new tool-calling shape — the malformed-JSON scenario no longer routes to `unknown` at all (that fallback now only fires when `message.tool_calls is None`, i.e. no tool selected). Not fixed yet — needs a decision on whether to re-wrap it or rely on tool-calling's schema validation being reliable enough in practice.
- [ ] **`limit` schema property has no `description` — same bug class as the `since_date.years` fix, not yet confirmed broken (found Session 35):** `build_tool_schemas()`'s `limit` property is `{"type": "integer"}` with no semantic guidance. A smoke test ("give me the top 5 hands...") resolved correctly, so it isn't proven broken — but there's no anchor for ambiguous phrasing. Stress-test with adversarial/ambiguous questions before deciding whether to add a `description`; don't fix speculatively without evidence.
- [ ] **`since_date` weekday-relative support (e.g. "since monday last week") — scoped but not built (Session 32):** raised mid-redesign as a real near-term need (same `since_date` label, not a separate `between_dates` param), then explicitly deferred for time. Confirmed the current design extends cleanly — `relativedelta`'s `weekday=` argument (e.g. `weekday=MO(-2)` for "the Monday before this week's Monday") is a JSON-serializability problem (the LLM can't emit a Python `MO(-2)` object directly, needs a plain value + a small lookup/construction step in Python), not a redesign of the month/day/years/months/days shape already shipped.
- [ ] **`gpt-4o-mini` non-determinism on `since_date` extraction at `temperature=0` (found Session 32, reconfirmed Session 35):** the exact same question ("...since november last year"), asked in separate runs (across sessions), produced different raw JSON — sometimes a spontaneous `"day"` matching today's day-of-month, sometimes `day` omitted (letting the `day=1` default apply as intended). Not currently blocking — the `day=1` default only fires when `day` is absent, and a spontaneous day matching today just narrows the range rather than producing a wrong year — but worth tracking if it causes a visibly wrong `since_date` in practice.

## Schema/capability gaps (found via Session 17's copilot-simulation exercise, 12 gaps mapped)
- [ ] Turn-street position flag unverified — is there a `flg_t_has_position`? Never checked against real schema.
- [ ] "Barrel" concept (cbet flop + no bet turn) — no confirmed flag for Hero's own turn-betting action.
- [ ] No conversational/session state — `main.py`'s loop and `parse_user_query()` are fully stateless; a follow-up like "ahora solo los pockets" can't be interpreted. Bigger architecture gap than the rest (would make the atomic-filter-recipe design trivial to extend, once it exists).
- [ ] `run_filter_query`'s SQL skeleton never JOINs `cash_limit` — no `amt_bb` for bb-denominated filter conditions.
- [ ] Atomic filter pieces (as designed) are fixed strings — no support for user-supplied numeric thresholds (e.g. "lost 5bb or more").
- [ ] "IP"/"OOP" ambiguous without a specified street — position is tracked per-street; a bare "ip" is underspecified. `llm_parser.py` design question: repromptable? convention-based default?
- [ ] "PFC" loses precision in multi-raise (4bp+) pots — `flg_p_first_raise=false` only says "not the opener," doesn't distinguish which raise Hero called into.
- [ ] Stake/limit filtering (e.g. "200NL") — needs the same `cash_limit` JOIN as above, plus a label→`amt_bb` mapping.
- [ ] No glossary for compressed poker shorthand notation (e.g. "B-X") in `llm_parser.py`'s system prompt.
- [ ] Board-texture/hand-reading analysis (e.g. "boards BW-L-L") — doesn't exist as a capability at all; would need new combinatorial logic on top of `poker_cards.py`. Flagged as an order-of-magnitude bigger gap — out of scope for now.
