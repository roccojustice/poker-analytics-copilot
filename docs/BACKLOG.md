## Next up (active)
- [ ] **v2 conversational filter composability — designed Session 37, unblocked Session 39, `action` field prototyped Session 41, one real bug open:** multi-turn spot-narrowing (e.g. "cbet flop" → "+ turn straight" → "+ turn flush" → "now 3bet pots ip pfr"). Design: 3 behaviors self-named and confirmed against his own example — **acumular** (AND-extend the current filter), **reemplazar** (discard and start fresh), **aclarar** (ask a disambiguating question before acting, when the new phrase could extend the current filter more than one way). Maps to the named NLP field **Dialogue State Tracking** (acumular ≈ slot filling, reemplazar ≈ context reset, aclarar ≈ clarification request). State: `active_filters`, a list of atomic filter *names*, held as a local variable in `main.py`'s loop (not a global — single-process/single-user, no cross-session persistence need) — **still not wired into `main.py`, only tested with a hardcoded string.** Mechanism: one added `action` field on the existing tool-calling schema (single LLM call, not a separate classifier call) — a 2-call planner/executor split is deferred until latency/accuracy evidence justifies the extra cost, not assumed upfront. **Session 41 progress:** `action` (enum `extend`/`replace`, English literals) added to the schema in `llm_parser.py` (uncommitted); `ask_clarifying_question` added as its own tool for the "aclarar" case, instead of relying on `tool_choice="auto"` returning free text. **Session 41 open bug, blocking:** live-tested against 3 real follow-up phrases with a hardcoded active filter — switching to a fully different query type (`winrate`, unrelated to the active hand-filter) still returned `action: "extend"`, which is meaningless. Needs either a sharper field `description` or a structural constraint tying `action` to whether the new `query_name`'s type matches the active filter's. Resolve this before wiring `active_filters` into `main.py`.
- [ ] **`json.JSONDecodeError` safety net lost in the tool-calling migration (found Session 36, 2026-08-21; revisited Session 37):** the old `parse_user_query()` wrapped `json.loads(content)` in a `try/except json.JSONDecodeError: return {"query_name": "unknown"}`. The rewritten version (`llm_parser.py:86`, `args = json.loads(tool_call.function.arguments)`) has no `try/except` around it — if the model ever returns a malformed `arguments` string, this now raises an uncaught `JSONDecodeError` instead of falling back to `"unknown"`. **Session 37 decision:** researched the `strict: true` Structured Outputs alternative (would force schema conformance instead of just re-adding a try/except) — found it requires a real schema refactor (every property becomes `"required"`, `"additionalProperties": false` on every nested object) and still doesn't cover `finish_reason == "length"` truncation. Weighed against the risk being purely hypothetical so far — **explicitly deferred, not fixing speculatively; monitor for a real occurrence in practice** before choosing re-wrap vs. `strict: true`.
- [ ] **`since_date` weekday-relative support (e.g. "since monday last week") — scoped but not built (Session 32):** raised mid-redesign as a real near-term need (same `since_date` label, not a separate `between_dates` param), then explicitly deferred for time. Confirmed the current design extends cleanly — `relativedelta`'s `weekday=` argument (e.g. `weekday=MO(-2)` for "the Monday before this week's Monday") is a JSON-serializability problem (the LLM can't emit a Python `MO(-2)` object directly, needs a plain value + a small lookup/construction step in Python), not a redesign of the month/day/years/months/days shape already shipped.
- [ ] **`gpt-4o-mini` non-determinism on `since_date` extraction at `temperature=0` (found Session 32, reconfirmed Session 35):** the exact same question ("...since november last year"), asked in separate runs (across sessions), produced different raw JSON — sometimes a spontaneous `"day"` matching today's day-of-month, sometimes `day` omitted (letting the `day=1` default apply as intended). Not currently blocking — the `day=1` default only fires when `day` is absent, and a spontaneous day matching today just narrows the range rather than producing a wrong year — but worth tracking if it causes a visibly wrong `since_date` in practice.
- [ ] **Extract `ATOMIC_FILTERS` + `FILTER_RECIPES` + `build_where_clause()` into their own module (decided Session 42, not implemented):** `db.py` is getting long and mixes two responsibilities. Move all three into one new single module owning "recipe name → `(where_sql, params)`"; `db.py` keeps only "execute SQL against Postgres" and imports the finished tuple. One file, not two — a recipe is a list of atomic *names*, meaningless without `ATOMIC_FILTERS`, so they're tightly coupled. Principle is cohesion / single responsibility (not "composability"). Precedent: `queries.py` is already a registry pulled out of its consumer. Cheap and reversible (`pytest` catches breakage, as in Session 39). When doing it: pick the module name, check for circular imports (`query_router.py` also imports `FILTER_RECIPES` for `is_filter_query()`/dispatch), run `pytest`.
